# BP16 C: public host device/state interface survey

Date: 2026-09-07. Layer: host virtualization API and QEMU device model, compared with guest firmware MMIO evidence. Decision: **HOLD** for implementing the missing device.

The surveyed public interfaces include real mechanisms for supplying virtual devices, GPU MMIO responses, and VM state. None establishes that the BP14 unknown device is one of those devices, or supplies its register/reset/read-side-effect contract. A host callback mechanism alone does not justify any particular read result. This is a bounded negative finding for the sources below, not a claim that Apple has no host device APIs.

The intended target remains the existing ARM64 macOS 27.0 / build 26A5425a recovery selection. This survey neither identifies the private node nor substitutes a different SoC or guest. No VM, native framework, TSS, or network-helper execution was performed. Public documentation was retrieved; no project source code, firmware, media, or start document was modified.

## QEMU version and current coverage

The inspected upstream base is commit `ff1d2d19d7e24893e2012d879f8e73077e17b9bd`; its [VERSION](https://github.com/qemu/qemu/blob/ff1d2d19d7e24893e2012d879f8e73077e17b9bd/VERSION) is **11.1.50**, a development-tree version. The project's running QEMU is a modified research worktree, not an unmodified release. The pinned [VMApple guide](https://github.com/qemu/qemu/blob/ff1d2d19d7e24893e2012d879f8e73077e17b9bd/docs/system/arm/vmapple.rst) documents Apple-Silicon macOS hosts, HVF, and an already installed macOS 12.x guest; this does not establish macOS 27 recovery support.

The base [machine construction](https://github.com/qemu/qemu/blob/ff1d2d19d7e24893e2012d879f8e73077e17b9bd/hw/vmapple/vmapple.c#L455) attaches a defined device set. Its [configuration device](https://github.com/qemu/qemu/blob/ff1d2d19d7e24893e2012d879f8e73077e17b9bd/hw/vmapple/cfg.c#L135) has a fixed property surface and reset behavior; it is not a general external register-provider interface. No inspected base property corresponds to the BP14 unknown target. Current runtime noncoverage comes from the existing BP14 transaction/flatview evidence, not from a new run in this survey.

The older `public-device-map-check.json` includes a pre-BP14 translation-unknown flag. The later BP14 same-event evidence and BP16 contract supersede that flag: the observed access is a four-byte read with a decode error, and its translated target has no runtime mapping. This does not establish device identity. Comparison-tree presence differences also do not establish semantics; this host survey does not rely on them.

## Current adapter comparison

The BP15 implementation, rather than the older BP8 `IMPLEMENTATION.md` snapshot, is the current contract:

- `nextcore/crates/nextcore-apls/src/runner.rs:62` distinguishes Native, raw TCG, and `TcgRecovery`. Recovery arguments at line 255 supply firmware/media/manifest/helper paths, restore roles, RAM/CPU, phase/total timeouts, and the explicit optional-RPC switch. There is no arbitrary device-state, MMIO callback, or VF handle argument.
- `x86/vmapple.py:392` validates one VM JSON bundle and preserves the identity/media association. `run_macosvm_native` at line 1074 runs an existing bundle through a native Apple-Silicon host. This is a separate backend; its host constraints are project policy, not a claim that every valid Apple host must always have the same OS major as its guest.
- `x86/vmapple.py:2345` forwards `optional_rpc_unavailable` to the existing research QEMU capability property. That negative-capability experiment does not define the later missing device or license inventing its return values.
- `x86/recovery_supervisor.py` owns the Linux worker lifecycle and receipts. `runner.rs:610` validates the supervisor and raw-launch identities, same-session PID evidence, input integrity, and cleanup, with recovery progress separate from kernel/userspace acceptance. A future device adapter must retain those distinctions; resolving a decode error or receiving bootx ACK is not macOS boot evidence.

No present host-adapter flag can legitimately be reinterpreted as the missing device's state. A native Virtualization.framework comparison on a compatible, explicitly supplied host could test a separate full-platform baseline, but it would not by itself publish the unknown register semantics or validate the TCG implementation.

## Gate for resuming implementation

**HOLD applies to this device implementation hypothesis.** To change it, provide a primary or independently implemented contract that ties the actual selected platform/device identity to the access range, width, reset state, read value, read side effects, and any ordering/error rules. If that contract names a host service, also identify the service API and lifecycle/serialization rules. Only then can a minimal adapter and the BP16 bounded same-event comparison be specified. Neither an unmapped read nor a generic callback API supplies those facts.

Exact private addresses, node strings, raw traces, and Apple payloads are absent from both survey outputs. No substitute zero-return device, alias, or firmware change was made.
